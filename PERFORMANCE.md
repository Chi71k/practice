# PERFORMANCE.md

Отчёт по Части 7–9 ДЗ «Context, Providers, custom hooks и оптимизация React».

## Методология измерений

**Уточнение к предыдущей версии этого файла.** React DevTools Profiler и встроенный React `<Profiler>` остаются документированной, рабочей частью React — предыдущая формулировка «React 19.2 полностью отключил classic-Profiler» была слишком категоричной. Точнее: в данном тестовом окружении расширение React DevTools при попытке записи в Timeline-режиме выдавало «Please use React Performance tracks instead of the Timeline profiler» — это сообщение самого расширения, а не признак того, что профилирование в принципе недоступно.

Вместо того чтобы полагаться на UI DevTools, измерения сняты через официальный программный API — компонент `<Profiler id="..." onRender={...}>` из пакета `react`. Он даёт ровно то, что требует ТЗ:

- `phase` — mount/update, то есть **факт коммита**;
- `actualDuration` — реальное время, потраченное на рендер поддерева в этом коммите (если дети сделали bailout через `memo`, здесь будут доли миллисекунды);
- `baseDuration` — оценка стоимости рендера того же поддерева **без всякой мемоизации** (эталон для сравнения).

`onRender` вызывался на каждый коммит подписанного поддерева (`AddResumeForm`, список `ResumeCard`), данные собирались через автоматизированный браузер (Playwright) на 60 засеянных резюме, инструментация полностью удалена из кода после снятия цифр. Дополнительно (как более грубый, но независимый сигнал) использовался `console.count()` в теле компонентов — он считает **дискретные вызовы функции-компонента**, а не стоимость; в отчёте ниже он приводится только там, где явно помечено, и не заменяет данные `<Profiler>`.

## 1. Какие компоненты рендерились до оптимизации?

До вынесения `ResumeCard` в отдельный `memo`-компонент карточки резюме рендерились как часть JSX прямо внутри `MyResumes` (`resumes.map(...)`). Это значит: при **любом** re-render `MyResumes` — ввод символа в поиск, смена фильтра, смена сортировки — React проходил по всем JSX-элементам функции заново, включая карту по всем резюме, и создавал новое виртуальное дерево для каждой карточки, даже если её данные не менялись.

Отдельно: до переноса резюме и профиля в Context, обе страницы либо сами читали `localStorage` при каждом монтировании (`Profile`), либо держали список в локальном `useState` (`MyResumes`) без единого источника правды — `Header` вообще не имел доступа к этим данным и не мог быть частью этой картины.

## 2. Где была обнаружена реальная лишняя работа?

Три конкретных места, все в `src/pages/MyResumes.jsx`, подтверждены данными `<Profiler>` из раздела 6:

- **Пересчёт списка.** `filterAndSortResumes(resumes, filters)` без `useMemo` выполняется прямо в теле компонента при каждом рендере.
- **Рендер карточек.** Без `memo` каждая карточка в `.map()` перерисовывается при любом re-render родителя. Замерено: `actualDuration` списка карточек на ввод одного символа в поиск — **14.4 ms без оптимизации** против **0.2 ms** после (при сопоставимом `baseDuration`, то есть реальная стоимость, а не только количество вызовов).
- **Форма добавления резюме перерисовывается от несвязанного поиска.** Найдено вживую через «Highlight updates» в React DevTools, затем подтверждено числами. `AddResumeForm` — сосед блока поиска/фильтров внутри `MyResumes`; её `onSubmit`-колбэк (`handleAdd`) создавался заново на каждый рендер `MyResumes` (без `useCallback`), из-за чего ввод в поиск лишний раз гонял всю форму (8+ полей). Починено: `AddResumeForm` обёрнута в `memo`, `handleAdd` — в `useCallback([addResume])`.

## 3. Где `useMemo` оказался полезен?

`src/pages/MyResumes.jsx`:

```js
const visibleResumes = useMemo(
  () => filterAndSortResumes(resumes, filters),
  [resumes, filters],
);
```

Почему `useMemo` уместнее, чем хранение результата в `state`: `visibleResumes` — это **производные данные** (100% выводятся из `resumes` и `filters`). Если бы это было отдельным `state`, пришлось бы вручную синхронизировать его дополнительным `useEffect` при каждом изменении `resumes` или `filters` — источник правды бы раздвоился, и легко было бы забыть один из кейсов синхронизации (например, забыть пересчитать после `deleteResume`). `useMemo` гарантирует, что результат всегда согласован с текущими `resumes`/`filters`, и просто не делает работу повторно, если оба входа не менялись между рендерами.

`filters` из `useResumeFilters` — тоже через `useMemo` (иначе новый объект `{search, city, ...}` на каждый рендер сделал бы зависимость `[resumes, filters]` бессмысленной — `useMemo` бы пересчитывался всегда).

## 4. Почему `useCallback` без `memo` часто не даёт пользы?

`useCallback` сам по себе не мешает ре-рендеру — он только сохраняет **ссылочную идентичность** функции между рендерами. Если компонент, которому передан этот callback, не обёрнут в `memo`, React всё равно перерисует его при каждом рендере родителя — стабильная ссылка на `onDelete` попросту некому проверять. Полезной комбинация становится только когда:

1. Потребитель обёрнут в `memo` (в проекте — `ResumeCard`);
2. `memo` использует **shallow-compare** пропсов, а не свою логику сравнения.

```js
const handleDelete = useCallback((id) => {
  deleteResume(id);
}, [deleteResume]);
```

Работает только в связке с `export default memo(ResumeCard)`. Замер (раздел 7) это подтвердил количественно: даже с включённым React Compiler, но без ручного `memo(ResumeCard)`, `actualDuration` списка карточек оставался пропорционален `baseDuration` (то есть реальный рендер каждой карточки продолжал происходить) — Compiler снизил стоимость каждого отдельного рендера, но не убрал сам рендер, в отличие от ручного `memo`, который даёт полный bailout.

## 5. Почему новый объект Provider `value` может ререндерить consumers?

`useContext` подписывает компонент на **ссылочные** изменения `value`. Если `Provider` рендерит `<Context value={{ profile, saveProfile, clearProfile }}>` без `useMemo`, то на **каждый** рендер самого `Provider`-компонента создаётся новый объект-литерал — новая ссылка — и React обязан разослать обновление всем consumers этого контекста, даже если `profile` внутри объекта не изменился (объект — не примитив, `Object.is(oldValue, newValue)` всегда `false` для нового литерала).

**Проверено экспериментально.** В `ProfileProvider`/`MyResumesProvider` собственных «случайных» ре-рендеров нет (они монтируются один раз в `AppProviders`, `children` — стабильная ссылка на `<App />`). Чтобы всё же увидеть эффект identity `value`, в `MyResumesProvider` был временно добавлен тикающий раз в секунду `state`, никак не связанный с резюме, и замерено число ре-рендеров `Header` (consumer обоих контекстов) за ~4.5 секунды (~4 тика):

| `useMemo` на `value` | React Compiler | Ре-рендеров `Header` за 4 тика |
|---|---|---|
| да | да | **0** |
| нет | да | **0** — Compiler сам восстановил стабильность `value` |
| да | нет | **0** — ручной `useMemo` работает независимо от Compiler |
| нет | нет | **4** — по одному ре-рендеру `Header` на каждый несвязанный тик |

Вывод: без `useMemo` и без Compiler объект `value` действительно рвёт стабильность на ровном месте и ре-рендерит consumers по причинам, вообще не связанным с данными профиля/резюме. Либо `useMemo`, либо Compiler (в этом простом случае) устраняют проблему; вместе — та же гарантия, продублированная.

## 7. Результаты после React Compiler

Дополнительно измерена промежуточная точка — **Compiler включён, но вся ручная мемоизация убрана** (`memo`/`useMemo`/`useCallback` сняты с `ResumeCard`, `AddResumeForm`, `visibleResumes`, `handleDelete`) — чтобы увидеть эффект именно Compiler в изоляции, тем же `<Profiler>`:

```text
Сценарий: поиск
До (без всего):        ResumeList actualDuration=14.40ms, baseDuration=13.00ms
Только Compiler:       ResumeList actualDuration=0.70ms,  baseDuration=2.50ms
После (memo+Compiler): ResumeList actualDuration=0.20ms,  baseDuration=17.00ms
```

```text
Сценарий: удаление
До (без всего):        ResumeList actualDuration=11.10ms, baseDuration=10.50ms
Только Compiler:       ResumeList actualDuration=0.30ms,  baseDuration=1.10ms
После (memo+Compiler): ResumeList actualDuration=0.10ms,  baseDuration=25.10ms
```

Ключевое наблюдение, которое даёт именно `actualDuration`/`baseDuration` (и которое не было видно через простой подсчёт вызовов `console.count`): **в варианте «только Compiler» `baseDuration` сам стал в разы меньше** (2.50ms и 1.10ms против 13.00/10.50ms без Compiler) — то есть Compiler удешевил **внутреннюю стоимость** рендера каждой карточки (закешировал промежуточные вычисления вроде `.find()` по `positionOptions` внутри `ResumeCard`). Но `actualDuration` при этом остаётся пропорционален новому, уже сниженному `baseDuration` (0.70/2.50 ≈ 28%, 0.30/1.10 ≈ 27%) — то есть **рендер по-прежнему реально происходит**, просто дешевле. Это ровно то, почему более ранняя версия отчёта на основе `console.count()` показывала «все карточки продолжают рендериться и с Compiler» — те замеры были правдой, просто не показывали, что каждый такой рендер уже подешевел.

Ручной `memo(ResumeCard)` даёт качественно другой эффект — не «дешевле», а «почти не выполняется» (`actualDuration` 0.20/0.10ms, на порядок меньше даже сниженного Compiler-baseDuration).

## 8. Какие ручные оптимизации Compiler сделал ненужными?

`memo(AddResumeForm)` и `useCallback(handleAdd)` — да, избыточны: `AddResumeForm` не участвует в сценариях поиска/фильтра/удаления вообще (несвязанный сосед), и после того как Compiler научился доказывать стабильность её единственного пропа `onSubmit`, лишних коммитов у неё нет ни с ручной обёрткой, ни без неё.

`memo(ResumeCard)` и `useMemo(visibleResumes)` Compiler **не заменяет** — по разделу 7, без них каждая карточка в `.map()` продолжает реально рендериться (Compiler лишь снижает стоимость этого рендера, не устраняет его).

## 9. Где ручная мемоизация оставлена и почему?

Оставлены **все** ручные оптимизации, включая формально избыточные (`memo(AddResumeForm)`, `useCallback(handleAdd)`) — они не мешают (Compiler их просто дублирует бесплатно), а убирать код, полагаясь на поведение конкретной версии Compiler, — риск без пользы для этого проекта.

`memo(ResumeCard)`, `useMemo(visibleResumes)` и `useCallback(handleDelete)` оставлены не «на всякий случай», а потому что измерение (раздел 7) прямо показало: без них список из 60+ резюме продолжает реально рендериться на каждое действие (Compiler делает это дешевле, но не бесплатно). Убирать их означало бы вернуть измеренную регрессию.

## 10. Что делает `useEffectEvent` и почему его нельзя использовать для подавления lint-предупреждения о зависимостях?

`useEffectEvent` (React 19.2) даёт способ вынести из эффекта кусок логики, который должен **всегда видеть последние значения** пропсов/state, но при этом **не должен** быть причиной пере-запуска самого эффекта. Функция, обёрнутая в `useEffectEvent`, не является реактивным значением — её не нужно (и не следует) указывать в массиве зависимостей `useEffect`, и в отличие от `useCallback` она всегда «видит» актуальные значения при вызове, без устаревшего замыкания (stale closure).

Почему его нельзя использовать просто как способ заглушить `exhaustive-deps` warning: правило `exhaustive-deps` существует, чтобы гарантировать, что эффект **реагирует** на все значения, от которых он зависит по смыслу. `useEffectEvent` не «обманывает» линтер — он меняет **семантику**: значение внутри Effect Event сознательно объявляется «не должно перезапускать эффект», а не «я не хочу с этим разбираться». Если применить его к значению, которое **должно** быть реактивным (например, `userId`, от которого зависит, какие данные грузить), эффект просто перестанет перезапускаться при смене `userId` — это баг, а не оптимизация. Правильное применение — только для значений вроде текущего таймаута/актуального колбэка уведомления, которые логически являются «сайд-каналом», а не входом эффекта.

В проекте `useEffectEvent` не использован — подходящего сценария (эффект, которому нужен свежий, но не реактивный колбэк) в текущем функционале нет; добавлять его «для галочки» ТЗ прямо запрещает.

## Инженерная заметка: баг `react-hook-form@7.82.0` + `React 19.2.6`

Не про производительность, но всплыло по ходу тестирования и стоит зафиксировать как воспроизводимый факт, а не голословное утверждение.

**Симптом.** `reset(values)` и `setValue(name, value)` из `react-hook-form` обновляют внутреннее состояние формы (`getValues()` отражает новое значение), но **не** пишут его обратно в DOM неконтролируемого `<input>` — видимое значение поля не меняется.

**Точные версии.** `react-hook-form@7.82.0`, `react@19.2.6`, `react-dom@19.2.6`, `vite@8.1.3`, `@vitejs/plugin-react@^6.0.1`.

**Минимальный воспроизводимый пример** (без Zod, без Context, без кастомных компонентов):

```jsx
import { useForm } from 'react-hook-form';

const ReproResetBug = () => {
  const { register, reset, setValue, getValues } = useForm({
    defaultValues: { fullName: '' },
  });

  return (
    <div>
      <input id="fullName" {...register('fullName')} />
      <button type="button" onClick={() => reset({ fullName: 'VIA_RESET' })}>
        reset
      </button>
      <button
        type="button"
        onClick={() => setValue('fullName', 'VIA_SET_VALUE', { shouldDirty: true, shouldTouch: true })}
      >
        setValue
      </button>
    </div>
  );
};
```

Шаги: набрать текст в поле → нажать «reset» → значение в поле не меняется (хотя `getValues()` возвращает `VIA_RESET`) → набрать текст заново → нажать «setValue» → результат тот же.

**Проверено в двух режимах сборки** — `npm run dev` и продакшен-сборка (`npm run build` + `npm run preview`) — результат идентичен в обоих, то есть это не артефакт Vite HMR/Fast Refresh, а поведение самой связки библиотек.

**Почему выбран обход через `key`, а не `reset(emptyValues)` внутри компонента формы.** Дело не в выборе API — `reset()` был первым, что опробовано, и именно он не сработал; `setValue()` как более точечная альтернатива тоже протестирована отдельно и тоже не работает. Оба официальных императивных способа синхронизировать значение с DOM в этой связке библиотек не работают, поэтому `Profile`-форма и форма добавления резюме размонтируются и монтируются заново через смену `key` — React в этом случае берёт значения из `defaultValues` при обычном (не императивном) первом рендере, что и работает надёжно. Это объясняет, почему `AddResumeForm` на сценарии «добавление» стабильно даёт несколько коммитов, а не один — часть из них это сам механизм обхода бага (submit текущего инстанса + размонтирование + монтирование нового с чистыми полями), а не лишняя работа.
