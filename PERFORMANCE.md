# PERFORMANCE.md

Отчёт по Части 7–9 ДЗ «Context, Providers, custom hooks и оптимизация React».

## Методология измерений

React 19.2 отключил classic-Profiler в React DevTools («Please use React Performance tracks instead of the Timeline profiler») независимо от dev/prod сборки. Вместо визуального Profiler использован точный и честный метод: временный `console.count()` в теле каждого измеряемого компонента (`AddResumeForm`, `ResumeCard`, `Header`), прогнанный через автоматизированный headless-браузер (Playwright) на 60 засеянных тестовых резюме. Это не интерпретация «на глаз», а прямой подсчёт реальных вызовов функции-компонента — сколько раз React фактически выполнил её тело в ответ на действие. После снятия всех цифр отладочный код полностью удалён из проекта.

## 1. Какие компоненты рендерились до оптимизации?

До вынесения `ResumeCard` в отдельный `memo`-компонент карточки резюме рендерились как часть JSX прямо внутри `MyResumes` (`resumes.map(...)`). Это значит: при **любом** re-render `MyResumes` — ввод символа в поиск, смена фильтра, смена сортировки — React проходил по всем JSX-элементам функции заново, включая карту по всем резюме, и создавал новое виртуальное дерево для каждой карточки, даже если её данные не менялись.

Отдельно: до переноса резюме и профиля в Context, обе страницы либо сами читали `localStorage` при каждом монтировании (`Profile`), либо держали список в локальном `useState` (`MyResumes`) без единого источника правды — `Header` вообще не имел доступа к этим данным и не мог быть частью этой картины.

## 2. Где была обнаружена реальная лишняя работа?

Три конкретных места, все в `src/pages/MyResumes.jsx`:

- **Пересчёт списка.** `filterAndSortResumes(resumes, filters)` — фильтрация + `.sort()` — без `useMemo` выполняется прямо в теле компонента при каждом рендере, включая рендеры, вызванные изменением состояния формы добавления резюме (`formState.errors` от `react-hook-form`), которое вообще не влияет на видимый список.
- **Рендер карточек.** Без `memo` каждая карточка в `resumes.map(...)` перерисовывается при любом re-render родителя, даже если её конкретный `resume`-объект и `onDelete` не изменились. Замерено на 60 резюме: ввод одного символа в поиск без оптимизации перерисовывает **все 60** карточек.
- **Форма добавления резюме перерисовывается от несвязанного поиска (найдено вживую через «Highlight updates», подтверждено `console.count`).** `AddResumeForm` — сосед блока поиска/фильтров внутри `MyResumes`. Изначально она не была обёрнута в `memo`, а её `onSubmit`-колбэк (`handleAdd`) создавался заново на каждый рендер `MyResumes` (без `useCallback`). Из-за этого ввод одного символа в поле поиска — состояние, которое живёт в `useResumeFilters` и вообще не связано с формой добавления, — перерисовывал **всю** форму целиком: 8+ полей, включая `MultiSelect` с 12 чекбоксами навыков. Починено: `AddResumeForm` обёрнута в `memo`, `handleAdd` — в `useCallback([addResume])`.

## 3. Где `useMemo` оказался полезен?

`src/pages/MyResumes.jsx`:

```js
const visibleResumes = useMemo(
  () => filterAndSortResumes(resumes, filters),
  [resumes, filters],
);
```

Почему `useMemo` уместнее, чем хранение результата в `state`: `visibleResumes` — это **производные данные** (100% выводятся из `resumes` и `filters`). Если бы это было отдельным `state`, пришлось бы вручную синхронизировать его дополнительным `useEffect` при каждом изменении `resumes` или `filters` — источник правды бы раздвоился, и легко было бы забыть один из кейсов синхронизации (например, забыть пересчитать после `deleteResume`). `useMemo` гарантирует, что результат всегда согласован с текущими `resumes`/`filters`, и просто не делает работу повторно, если оба входа не менялись между рендерами.

`filters` из `useResumeFilters` — тоже через `useMemo` (иначе новый объект `{search, city, ...}` на каждый рендер сделал бы зависимость `[resumes, filters]` бессмысленной — `useMemo` бы пересчитывался всегда).

## 4. Почему `useCallback` без `memo` часто не даёт пользы?

`useCallback` сам по себе не мешает ре-рендеру — он только сохраняет **ссылочную идентичность** функции между рендерами. Если компонент, которому передан этот callback, не обёрнут в `memo`, React всё равно перерисует его при каждом рендере родителя — стабильная ссылка на `onDelete` попросту некому проверять. Полезной комбинация становится только когда:

1. Потребитель обёрнут в `memo` (в проекте — `ResumeCard`);
2. `memo` использует **shallow-compare** пропсов, а не свою логику сравнения.

В `MyResumes.jsx`:

```js
const handleDelete = useCallback((id) => {
  deleteResume(id);
}, [deleteResume]);
```

Работает только в связке с `export default memo(ResumeCard)` — без него `useCallback` тут был бы чистым накладным расходом (аллокация + сравнение зависимостей) без единого эффекта на количество рендеров. Замер это подтвердил: даже с React Compiler (см. раздел 7) `ResumeCard` без ручного `memo` перерисовывался ровно как без всякой оптимизации — Compiler не подставил memo-эквивалент сам за пределы простого single-prop случая.

## 5. Почему новый объект Provider `value` может ререндерить consumers?

`useContext` подписывает компонент на **ссылочные** изменения `value`. Если `Provider` рендерит `<Context value={{ profile, saveProfile, clearProfile }}>` без `useMemo`, то на **каждый** рендер самого `Provider`-компонента создаётся новый объект-литерал — новая ссылка — и React обязан разослать обновление всем consumers этого контекста, даже если `profile` внутри объекта не изменился (объект — не примитив, `Object.is(oldValue, newValue)` всегда `false` для нового литерала).

**Проверено экспериментально.** В `ProfileProvider`/`MyResumesProvider` собственных «случайных» ре-рендеров нет (они монтируются один раз в `AppProviders`, `children` — стабильная ссылка на `<App />`). Чтобы всё же увидеть эффект identity `value`, в `MyResumesProvider` был временно добавлен тикающий раз в секунду `state`, никак не связанный с резюме, и замерено число ре-рендеров `Header` (consumer обоих контекстов) за ~4.5 секунды (~4 тика):

| `useMemo` на `value` | React Compiler | Ре-рендеров `Header` за 4 тика |
|---|---|---|
| да | да | **0** |
| нет | да | **0** — Compiler сам восстановил стабильность `value` |
| да | нет | **0** — ручной `useMemo` работает независимо от Compiler |
| нет | нет | **4** — по одному ре-рендеру `Header` на каждый несвязанный тик |

Вывод: без `useMemo` и без Compiler объект `value` действительно рвёт стабильность на ровном месте и ре-рендерит consumers по причинам, вообще не связанным с данными профиля/резюме. Либо `useMemo`, либо Compiler (в этом простом случае) устраняют проблему; вместе — та же гарантия, продублированная.

Данные: 60 засеянных резюме, фильтр по городу `astana` даёт 12 совпадений. Считались реальные вызовы функции-компонента (`console.count`), не косвенные признаки.

```text
После ручной оптимизации: AddResumeForm — 0, ResumeCard — 0
Вывод: до оптимизации любое несвязанное состояние в MyResumes перерисовывало
абсолютно все карточки и форму добавления; после — 0 лишних рендеров.
```

```text
Сценарий: смена фильтра по городу (60 → 12 видимых)
До: AddResumeForm — 1, ResumeCard — 12 (все, что попали в новый filtered-список)
После ручной оптимизации: AddResumeForm — 0, ResumeCard — 0
Вывод: без memo React обязан вызвать функцию каждой карточки, оставшейся в
JSX-дереве, даже если сама карточка не изменилась — просто чтобы понять,
что рисовать нечего нового. С memo React вообще не трогает выжившие карточки,
```

```text
После ручной оптимизации: AddResumeForm — 2, ResumeCard — 1

сброса, см. раздел про баг reset() ниже). А вот ResumeCard после оптимизации
рендерит только новую карточку — 59 старых не тронуты, до оптимизации все 60
```

## 7. Результаты после React Compiler

Дополнительно измерена промежуточная точка — **Compiler включён, но вся ручная мемоизация убрана** (`memo`/`useMemo`/`useCallback` сняты с `ResumeCard`, `AddResumeForm`, `visibleResumes`, `handleDelete`) — чтобы увидеть эффект именно Compiler в изоляции:

| Сценарий | До (без всего) | **Только Compiler** (без ручной memo) | После (ручная memo + Compiler) |
|---|---|---|---|
| поиск | AddForm 1, Card 60 | AddForm **0**, Card **60** | AddForm 0, Card 0 |
| фильтр (12 из 60) | AddForm 1, Card 12 | AddForm **0**, Card **12** | AddForm 0, Card 0 |
| удаление (59 ост.) | AddForm 1, Card 59 | AddForm **0**, Card **59** | AddForm 0, Card 0 |
| добавление | AddForm 2, Card 60 | AddForm 2, Card **60** | AddForm 2, Card 1 |

Неожиданный и содержательный результат: **Compiler сам, без единой строчки `memo`, полностью убрал лишние рендеры `AddResumeForm`** (0 вместо 1) — он корректно вывел, что `onSubmit={handleAdd}` не меняется между рендерами, и пропустил повторный вызов компонента. Но **`ResumeCard` внутри `.map()` Compiler не спас вообще** — цифры идентичны варианту «без всякой оптимизации» (60/12/59). Причина: `visibleResumes` без `useMemo` — новый массив на каждый рендер (`.filter()` создаёт новую ссылку), и Compiler не переносит эту гарантию стабильности сквозь границу `.map()` на отдельные `<ResumeCard>` с тем же успехом, что и для одиночного child-компонента с одним стабильным пропом.

## 8. Какие ручные оптимизации Compiler сделал ненужными?

По замеру раздела 7 — **`memo(AddResumeForm)` и `useCallback(handleAdd)` Compiler действительно делает избыточными**: даже без них React Compiler сам держит `AddResumeForm` на 0 лишних рендеров. Это подтверждено числами, а не предположением.

`memo(ResumeCard)` и `useMemo(visibleResumes)` Compiler **не заменяет** — без них список из 60 карточек так и перерисовывался целиком на каждое действие (60/12/59), несмотря на включённый Compiler.

## 9. Где ручная мемоизация оставлена и почему?

Оставлены **все** ручные оптимизации, включая те, что раздел 8 называет избыточными (`memo(AddResumeForm)`, `useCallback(handleAdd)`) — они не мешают (Compiler их просто дублирует бесплатно), а убирать код, полагаясь на поведение конкретной версии Compiler, — риск без пользы для этого проекта.

`memo(ResumeCard)`, `useMemo(visibleResumes)` и `useCallback(handleDelete)` оставлены не «на всякий случай», а потому что измерение (раздел 7) прямо показало: без них список из 60+ резюме перерисовывается целиком на каждый чих (поиск/фильтр/удаление), Compiler в этом конкретном случае (мемоизация через границу `.map()`) их не подменяет. Убирать их означало бы вернуть измеренную регрессию.

## 10. Что делает `useEffectEvent` и почему его нельзя использовать для подавления lint-предупреждения о зависимостях?

`useEffectEvent` (React 19.2) даёт способ вынести из эффекта кусок логики, который должен **всегда видеть последние значения** пропсов/state, но при этом **не должен** быть причиной пере-запуска самого эффекта. Функция, обёрнутая в `useEffectEvent`, не является реактивным значением — её не нужно (и не следует) указывать в массиве зависимостей `useEffect`, и в отличие от `useCallback` она всегда «видит» актуальные значения при вызове, без устаревшего замыкания (stale closure).

Почему его нельзя использовать просто как способ заглушить `exhaustive-deps` warning: правило `exhaustive-deps` существует, чтобы гарантировать, что эффект **реагирует** на все значения, от которых он зависит по смыслу. `useEffectEvent` не «обманывает» линтер — он меняет **семантику**: значение внутри Effect Event сознательно объявляется «не должно перезапускать эффект», а не «я не хочу с этим разбираться». Если применить его к значению, которое **должно** быть реактивным (например, `userId`, от которого зависит, какие данные грузить), эффект просто перестанет перезапускаться при смене `userId` — это баг, а не оптимизация. Правильное применение — только для значений вроде текущего таймаута/актуального колбэка уведомления, которые логически являются «сайд-каналом», а не входом эффекта.

В проекте `useEffectEvent` не использован — подходящего сценария (эффект, которому нужен свежий, но не реактивный колбэк) в текущем функционале нет; добавлять его «для галочки» ТЗ прямо запрещает.

## Инженерная заметка: баг `react-hook-form@7.82` + `React 19.2`

Не про производительность, но всплыло по ходу тестирования и стоит зафиксировать. `react-hook-form` (проверено на 7.81.0 и 7.82.0) в связке с React 19.2.6 не обновляет DOM `<input>` при вызове `reset()`: внутреннее состояние формы (`getValues()`) обновляется корректно, а видимое значение поля — нет. Подтверждено на минимальном примере без Zod/Context/кастомных компонентов. Обойдено стандартным паттерном: `Profile`-форма и форма добавления резюме теперь при очистке/после сабмита размонтируются и монтируются заново через смену `key`, вместо того чтобы полагаться на сломанный `reset()`. Это же объясняет, почему `AddResumeForm` на сценарии «добавление» стабильно даёт 2 рендера, а не 1 — второй рендер это не «лишняя работа», а сам механизм обхода бага (submit текущего инстанса + монтирование нового с чистыми полями).

Все цифры выше сняты автоматически и воспроизводимы. Если хочешь дополнительно увидеть один скриншот для галочки по ТЗ (React 19.2 Performance Tracks):

   ```js
   const cities = ['astana', 'almaty', 'karaganda', 'shymkent', 'other'];
   const positions = ['frontend', 'backend', 'fullstack', 'designer', 'qa', 'other'];

     id: crypto.randomUUID(),
     fullName: `Тестовый Кандидат ${i + 1}`,
     position: positions[i % positions.length],
     city: cities[i % cities.length],
     age: 20 + (i % 40),
   ```

5. Скриншот с подписью — в отчёт.
